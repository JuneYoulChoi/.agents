🗺️ 요청이 경로로 바뀌는 과정

요청 하나가 여러 분기로 이어질 수 있습니다. 하네스는 필요한 결과를 모아 함께 검증합니다.

  1. 🔎요청 분류분야 · 작업 유형 · 위험 · 깊이
  2. 🧱기준선 확인문서 · 요구사항 · 변경 영향
  3. 🔀필요한 분기 열기기술 · 설정 · 시험 · 설계
  4. ✅결과 합치기구현 · 검증 · 인계
프로젝트 상태에 따라 바뀌는 경로

신규 요구사항과 설계 방향을 정합니다. 기존 기준선과 변경 영향을 확인합니다.

혼합 두 경로를 함께 적용합니다. 미확인 기준선을 찾는 동안 읽기 전용으로 조사합니다.

작업을 나누는 5개 레이어

요청·맥락 → 작업 구성 → 라우팅·게이트 → 실행 → 검증·피드백

하네스는 전 과정에서 경로를 다시 판단할 수 있습니다. G3에서 작업 단위와 역할을 정하고, 권한과 효과를 확인한 범위에서 독립된 작업을 맡깁니다.

🧰 도구와 권한

어댑터가 사용 가능한 도구와 권한을 확인하고, 실행 결과를 증거로 남깁니다.

🔀

Router

구조화한 요청에서 게이트, 스킬, 검증 요구를 계산합니다.

📒

Runner

강제 모드에서 게이트 증거와 작업 상태를 기록합니다.

🔌

Codex · Claude

모델과 추론 수준을 연결하고, 허용된 도구로 스킬을 수행합니다.

🧪

검증 도구

G4에서 방법과 환경을 고릅니다. 해당 환경에서 실행한 결과를 G7에서 확인합니다.

설치와 가드가 필요한 때

Bootstrap은 공용 템플릿과 두 런처를 설치합니다. 기존 사용자 파일과 소스 지문을 확인합니다.

현재 훅 차단 증거나 유효한 수동 가드가 있으면 강제 모드를 적용합니다. 가드 없는 일반 변경은 권고 모드로 진행하고 마무리 검사를 실행합니다.

권고 모드에서 큰 변경이 필요하면 임시 강제 여부를 확인합니다. 어댑터가 강제 수준을 지원하지 않는 환경은 읽기 전용입니다.

G7은 수용 기준별 실행 결과를 확인하고, 실패하면 원인에 가장 가까운 게이트를 다시 엽니다.

요구사항·QAS→설계·ADR→구현 파일→시험 ID→검증 결과
↶ G7에서 시험 계획에 공백을 찾았다면

G4를 다시 열어 계획을 보완합니다. 여전히 유효한 결과는 그대로 쓰고, 영향을 받은 검증만 다시 실행합니다. 현재 단계는 jydlc status로 확인합니다.

표준 적용과 하네스 갱신

아키텍처, 요구사항, 생명주기 등 변경에 필요한 표준을 고르고 적용 근거를 기록합니다. 공식 적합성에는 표준 원문과 조항별 증거가 필요합니다.

하네스 자체를 바꿀 때는 계획과 영향을 확인하고 승인을 받습니다. 변경 후 검증을 마치고 이 안내서를 갱신합니다.
