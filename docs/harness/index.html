1. Why 관찰됨

세션이 바뀌어도 의도와 설계 근거가 사라지지 않게 한다

이 하네스는 요청을 먼저 분류하고, 필요한 스킬만 읽고, 요구사항에서 테스트와 문서까지의 연결을 남기는 공통 작업 방식입니다. 대화의 기억이나 특정 프로젝트 경로·클라우드·패키지에 의존하지 않는 것을 목표로 합니다.

목표

Greenfield·Brownfield·Hybrid 작업을 증거와 승인으로 구분하고, 작은 변경도 추적 가능한 산출물로 남깁니다.

비목표

모든 작업에 과도한 문서나 다중 에이전트를 강제하지 않습니다. 명확하고 가역적인 작은 작업은 가볍게 진행합니다.

핵심 태도

관찰된 사실, 추론, 가정을 분리합니다. 제품 가치나 권한이 필요한 결정은 사용자의 확인 없이 확정하지 않습니다.

2. Architecture 관찰됨

안전 규칙에서 플랫폼 어댑터까지, 아래 계층만 의존한다

결정적 해석과 점진적 로딩

Router는 처음에는 승인된 스킬의 메타데이터만 읽습니다. 선택된 스킬과 그 스킬이 명시한 자료만 이어서 읽으며, 해상도 순서는 project_reviewed → shared_reviewed → core_fallback입니다.

격리 원칙

incoming/은 내려받은 후보의 격리 장소입니다. 활성 경로는 skills/와 Registry뿐이며, 격리 후보는 자동 실행하지 않습니다.

라우팅은 트리 분류 + MIMO 게이트 + DAG 실행

G0 guard → G1 intake → G2 baseline → G3 workflow → G4 concern → G5 specialist → G6 assembly/execution → G7 verification/handoff

분류 체계는 계층형이지만 한 요청은 여러 필드를 가질 수 있습니다. 각 게이트는 여러 증거와 산출물을 입력으로 받아 여러 스킬을 활성화·후보화·억제·차단하고, 활성화된 본문만 읽습니다. 검증 실패나 새 증거는 가장 가까운 원인 게이트로 역전파되어 의존하는 하위 산출물만 재계산합니다. 이는 학습 가중치를 가진 모델이 아니라 설명 가능한 결정적 라우팅 그래프입니다.

G0–G7 routing manifest

최소 참조 실행부

Router가 스킬을 고르고, 고정 stage Runner가 한 번에 하나의 다음 스킬을 반환합니다. State store는 목표·성공 조건·분류·선택 스킬·artifact/evidence·revision을 대상 프로젝트에 원자적으로 저장하고, Validator가 intake/route/result/state/config 계약을 검사합니다. Bootstrap은 공유 source와 분리된 기존 target에 Codex/Claude wrapper와 pin된 config만 설치합니다.

플랫폼 경계

자연어 해석과 실제 SKILL.md 수행은 Codex/Claude가 담당합니다. Python 참조 구현은 JSON 계약의 한 provider이며 대상 프로젝트나 native adapter의 필수 언어가 아닙니다.

3. Traceability 관찰됨

요구에서 실행·검증·문서까지 연결한다

PRD/SRS → external entity/interface → UC → FA → QA/QAS → HLD → ADR → TECH → IMPL → LLD / CONFIG → task/code/tests/docs/operations

여기서 FA는 Functional Architecture, QA는 Quality Attribute, QAS는 측정 가능한 Quality Attribute Scenario를 뜻합니다. TECH는 목적·종류·상태·호환성·통합 관계를, IMPL은 모듈·생태계 바인딩·구현 언어·생성 코드 소유권·검증을 기록합니다. CONFIG는 외부화가 정당한 설정의 타입·소스·우선순위·검증·시크릿·호환성 계약입니다.

선택

technology-selection-and-integration이 UC·FA·QAS에서 capability를 도출하고, 기술을 mandated/existing/candidate/selected/rejected 등으로 구분합니다. 이름이 언급되거나 설치됐다는 사실만으로 채택하지 않습니다.

생태계 규약

선택되거나 실제 영향받은 ROS 2·Node.js·React·gRPC·Isaac Lab·Docker·Isaac Sim·MoveIt·Kubernetes·Modbus·colcon 스킬만 로드합니다. 각 스킬은 구조·규약·안티패턴·호환성·검증을 담당합니다.

구현 언어

language-engineering이 변경되는 authored boundary에만 C/C++/C#/Rust/Go/Java/Python/JavaScript/TypeScript/HTML/CSS/Shell profile을 적용합니다. 생성 코드는 schema/toolchain 소유입니다.

아키텍처 게이트: 소프트웨어 관련 요청은 사용자가 문서를 언급하지 않아도 docs/architecture/를 확인합니다. 없거나 오래됐으면 코드 기반 초안을 만들 수 있지만, UC·FA·QA·외부 인터페이스·모듈 경계의 중요한 결정은 사용자 확인이 필요합니다.

4. Sequence 관찰됨

모든 요청은 분류부터, 구현은 근거와 승인 이후에

  1. 1. Intake범위·상태·필드·행동·위험·깊이 분류
  2. 2. Clarification가치·권한·제약의 불명확성을 사용자에게 질의
  3. 3. Discovery현재 동작·문서·계약·테스트 근거 수집
  4. 4. ArchitecturePRD/SRS~LLD와 뷰/다이어그램 기준선 확인
  5. 5. Impact변경 영향과 회귀 범위 확인
  6. 6. AssemblyTECH 선택 → 영향받는 생태계 규약 → authored 언어 profile → 조건부 CONFIG의 최소 스킬 구성
  7. 7. Deliberation증거 중심 합의, 최대 3라운드 후 사용자 승격
  8. 8. DesignADR·TECH·IMPL·CONFIG·작업 단위·수락 기준·테스트 계획
  9. 9. Execution작고 응집된 단위로 구현·문서 동기화
  10. 10. Verify / Handoff검증 근거·잔여 위험·재개 가능한 인계
Forward / backward: 정상 진행은 G0에서 G7까지 하나의 forward revision으로 기록합니다. 실패가 구현 결함이면 G6, 생태계·언어 결함이면 G5, 기술·설정 공백이면 G4, 아키텍처 모순이면 G2로 되돌아갑니다. 독립적으로 유효한 branch는 보존하며, 같은 중요 이슈가 새 근거 없이 3회 반복되면 사용자에게 승격합니다.
프로젝트 상태기본 경로수정 전 필수 확인
Greenfield아키텍처 기준선 → 요구·QAS·ADR·작업 계획목표, 사용자, 범위, 품질 시나리오
Brownfield아키텍처 기준선 → 영향 분석 → 설계/구현현재 동작, UC, 계약, 모듈, 테스트, 문서, 회귀 범위
Hybrid기존 영향 분석과 신규 능력 계획을 의존 순서로 분리extend / new / mixed 근거
Unknown읽기 전용 Discovery 후 재분류기준선 확보 전 물질적 수정 금지

5. Gates 관찰됨

멈춰야 할 때는 명시적으로 멈춘다

의도·명확성

목표, 성공 조건, 제약, 대상, 방향이 중요한 수준으로 불명확하면 질문합니다.

권한·행동

배포, 데이터 변경, 비용, 자격증명, 외부 발행, 파괴적 동작은 범위가 있는 명시적 승인이 필요합니다.

아키텍처·영향

소프트웨어 변경 전 아키텍처 기준선과 Brownfield 영향/회귀 기록을 확인합니다.

설정·환경

IP·Port·URL·경로·Timeout·Secret·공개 client bootstrap·theme token 같은 후보를 코드/빌드/배포/런타임/시크릿으로 분류하고, 외부화할 값은 타입·우선순위·검증·소유자를 갖춰야 합니다. 도구 인기도는 같은 생태계·기능 안에서만 비교하며 의존성을 자동 승인하지 않습니다.

문서 공백

필요 문서가 없으면 목적·대상·위치가 분명할 때 최소 문서를 만들고, 아니면 용도를 묻습니다.

검증·완료

검증하지 않은 완료는 완료가 아닙니다. 미실행 검사는 통과로 표시하지 않고 잔여 위험을 남깁니다.

역전파·재계산

검증 실패·새 증거·사용자 정정·capability 손실은 가장 가까운 원인 게이트를 다시 엽니다. immutable gate result와 event를 남기고, trace로 연결된 하위 산출물만 stale 처리하며 의도·승인·무관한 branch는 보존합니다.

다중 에이전트

독립된 전문성 또는 병렬 증거가 실제로 도움이 될 때만 사용합니다. 최종 책임은 Router에 남습니다.

6. Bootstrap and enforcement 관찰됨

플랫폼 파일은 얇게, 정책은 공유 계약과 상태가 소유한다

Canonical templates

Codex AGENTS.md.tmpl와 Claude CLAUDE.md.tmpl가 유일한 부트스트랩 원천입니다. 대상 프로젝트에는 얇은 관리 파일만 렌더링합니다.

Project boundary

harness.json이 핀된 소스·템플릿·Registry·상태 루트·어댑터를 기록합니다. Git 루트는 경로 힌트일 뿐 Greenfield/Brownfield 판정이 아닙니다.

Safe fallback

hook, manual, unsupported를 명시합니다. manual은 신선한 manual guard/action 기록이 있을 때만 상태 저장과 제한적 가역 workspace 변경을 허용하고, unsupported는 ephemeral/read-only입니다. 모든 모드에서 고위험·외부·파괴적 작업은 멈춥니다. 스킬·문서가 없거나 의도가 불명확하면 탐색적 확장인지 사용자 방향을 따를지 먼저 묻습니다.

Install and upgrade

명시적 target root를 우선하고, 모호한 저장소·중첩 루트·탈출 경로를 거부합니다. 복사가 기본이며 동일 해시는 멱등입니다. 사용자 파일이나 편집된 관리 파일은 덮어쓰지 않고 충돌을 보고합니다. 설치는 lock·원자적 트랜잭션·롤백 기록을 가지며 UTF-8 LF 정규화 후 32KiB를 넘거나 placeholder가 남으면 실패합니다.

State

작업 상태는 대상 프로젝트의 .agents/state/<task-id>/에만 둡니다. 공유 하네스 소스와 대상 런타임 상태를 혼동하지 않습니다.

8. Upgrade path 관찰됨

하네스 자체를 바꿀 때는 먼저 현재 설계를 보존 대상으로 삼는다

intake → harness-upgrade-analysis → user approval → implementation → verification → harness-overview-html → handoff

  1. plan/ 전체와 활성 Registry를 기준선으로 읽습니다.
  2. 관련 파일을 unchanged, patch, extend, wrapper, replace, deprecate, new으로 분류합니다.
  3. 기존 게이트·시퀀스·전환 계약을 기본으로 보존하고, 물질적 변경은 사용자 승인 후에만 적용합니다.
  4. Fixture·호환성·롤백 계획을 검증하고 Registry와 plan을 함께 동기화합니다.
  5. 이 HTML을 재생성해 사람용 설명을 최신 기준선에 맞춥니다.

9. Use and resume 관찰됨

개발자는 목표를 말하고, 하네스는 필요한 결정을 다시 묻는다

권장 요청 형식

Goal: 바꾸거나 이해할 것 · Context: 신규/기존 프로젝트와 관련 경로 · Success: 완료 판단 · Constraints: 호환성/기술/보안/범위 · Output: 코드·테스트·설계·문서

사용자는 JSON을 작성하지 않습니다. Codex/Claude가 intake skill로 위 내용을 구조화하고 Validator와 Runner에 전달합니다.

재개

대상 프로젝트의 .agents/state/TASK-<id>/ 아래 state.json, events.ndjson, handoff.md, artifacts.json을 기준으로 다음 세션에서 재개합니다. 읽을 수 없거나 다른 프로젝트의 상태는 원본을 보존한 채 거부합니다.

상태

active, waiting_user, blocked, failed, cancelled, complete

사용자 답변이 필요한 상태는 침묵으로 승인되지 않습니다.
