01 · The problem

긴 세션의 문제가 아니라, 사라지는 기준선의 문제입니다.

세션이 바뀌어도 최초 요구사항, UC, FA, QA, 아키텍처 결정과 테스트 근거가 같은 방향을 가리켜야 합니다.

FAILURE 01

Prompt drift

대화가 길어질수록 처음의 목표와 제약이 최신 변경에서 희미해집니다.

FAILURE 02

Context roulette

새 세션이 문서를 읽지 않거나 코드만 보고 제품 의도를 추측할 수 있습니다.

FAILURE 03

Skill overload

모든 모범 사례를 동시에 적용하면 작은 작업도 복잡해집니다.

DESIGN RESPONSE

기억 대신 계약, 지시 대신 게이트

자연어 요청을 구조화된 intake로 바꾸고, 결정적 게이트가 필요한 스킬만 선택하며, 산출물과 증거를 target-local state에 연결합니다.

NON-GOAL

거대한 범용 플랫폼이 아님

특정 클라우드·언어·프레임워크를 강제하거나 모든 환경을 하나의 구현으로 덮지 않습니다.

02 · Global rules

모든 세션이 공유하는 불변 조건.

작은 작업은 가볍게, 중요한 결정은 증거와 승인으로 무겁게 다룹니다.

의도·성공 기준

목표, 범위, 제약, 완료 조건을 먼저 구조화합니다.

불명확성 처리

자료에 없는 경우 탐색적 확장인지 사용자의 컨셉·방향을 따를지 묻습니다.

프로젝트 상태

Greenfield, Brownfield, Hybrid, Unknown을 증거로 판정합니다.

아키텍처 우선

소프트웨어 변경 전 docs/architecture/와 실제 코드를 확인합니다.

추적성·문서 공백

요구→설계→구현→테스트를 연결하고 필요한 최소 문서를 만듭니다.

권한·최소 변경

승인 범위를 확장하지 않고 안전한 최소 변경을 선택합니다.

검증 없는 완료 금지

미실행 검사는 통과가 아니며 가정과 잔여 위험을 남깁니다.

환경 설정 가능성

IP·Port·URL·timeout·secret은 필요할 때 타입과 우선순위를 갖춰 외부화합니다.

최소 충분 스킬

라우팅 근거가 있는 branch만 읽고 인기도나 단순 언급으로 활성화하지 않습니다.

“Simple rules, many compositions.” 규칙을 무한히 늘리기보다, 다중 입력으로 필요한 규칙 조합을 정확히 선택합니다.
03 · System architecture

큰 흐름은 5개 레이어, 실행 제어는 G0–G7.

Codex와 Claude는 같은 계약을 다른 방식으로 실행할 수 있고, 대상 프로젝트는 공유 하네스 소스와 분리됩니다.

1 · 요청·맥락

목표·완료 조건·필드·위험과 기존 구조를 확인합니다. G1–G2.

2 · 작업 경로

작업 유형, 필요한 단계, 깊이, 의존성과 역할을 구성합니다. G3.

3 · 라우팅·게이팅

G0–G7 한 곳에서 활성 분기와 진행 조건을 제어합니다.

4 · 실행

분야·기술·언어 스킬과 실제 도구를 연결합니다. G4–G6.

5 · 검증·피드백

현재 결과를 검증하고 영향받은 부분만 다시 검토합니다. G7.

공통 통제

권한, 출처·신뢰, 상태·증거, SOLID·GRASP 등 해당 품질 기준은 전체에 적용합니다.

아래 L0–L7은 구현 구성요소 구분이며, 추가 실행 단계나 항상 켜진 에이전트가 아닙니다.

두 개의 루트

Harness source는 plan·skills·registry·scripts를, Target project는 코드·architecture docs·state를 소유합니다. 서로 중첩하지 않습니다.

두 개의 시간축

Stage는 사람의 작업 여정이고 Gate는 기계의 선택 네트워크입니다. 함께 움직이지만 같은 개념은 아닙니다.

04 · Architecture trace

요구사항에서 코드까지 끊기지 않는 설계 척추.

UC가 시스템 행동을, FA가 기능 분해를, QA/QAS가 품질 압력을 만들고, ADR과 패턴 선택이 설계 근거를 보존합니다.

PRD · SRS문제, 범위, stakeholder, 요구
External boundaryentity · interface · trust
UCactor, trigger, flow, acceptance
FA · QA/QAS기능 분해와 품질 시나리오
HLD · ADR · Pattern구조, 결정 근거, trade-off
LLD · Code · Test모듈, 설정, 검증 증거
다이어그램 텍스트 설명

상단의 요구, 행동, 기능/품질, 표준/구조, 상세 결정이 좌에서 우로 연결되고 layer/module, C&C/sequence, infrastructure/deployment, class/data/API 뷰로 구체화됩니다.

문서가 없다면: 코드 분석으로 code-derived draft를 만들 수 있습니다. 그러나 UC, FA/QA, 모듈 경계처럼 제품 의미를 바꾸는 결정은 사용자 확인 없이 사실로 승격하지 않습니다.
05 · Routing network

트리처럼 단순하고, 네트워크처럼 조합됩니다.

하나의 질문은 코드·문서·설정·기술 통합일 수 있습니다. 각 branch는 독립된 활성화 근거를 가져야 합니다.

왜 이 스킬들이 선택되는가

기존 시스템 변경이라 영향 분석이 먼저이고, 실제 통합 대상인 ROS 2와 gRPC, 작성되는 C++, 환경별 endpoint 설정, API/분산 실패 위험만 활성화됩니다. 단순히 저장소에서 발견된 기술은 선택되지 않습니다.

Greenfield

사용자·문제·scope부터 PRD/SRS, UC, QAS, architecture와 delivery plan으로 전개합니다.

Brownfield

기존 UC·FA·QA·API·회귀 동작을 기준선으로 잡고 영향과 호환성을 먼저 조사합니다.

Hybrid / Unknown

기존과 신규 영역을 분리하거나 안전한 read-only discovery 후 다시 분류합니다.

07 · Selective quality

Clean Code, SOLID, GRASP—필요한 곳에만 깊게.

작성 코드에는 correctness·clarity·error handling·testability core가 기본입니다. 추가 원칙은 이름이 아니라 실제 위험과 경계로 선택합니다.

설정

code constant, build-time, deploy-time, runtime, secret으로 분류합니다. 모든 상수를 설정 파일로 보내지 않습니다.

국제 표준

guidance, alignment, evidenced conformance를 구분합니다. 공식 적합성에는 권한 있는 원문·scope·evidence·deviation owner가 필요합니다.

멀티 에이전트 결과 합류와 작은 문맥

현재 스킬에 배정된 작업만 준비하고 의존성·점유 경로·동시 실행 수를 확인합니다. 네이티브 도구가 실행하며 Runner는 직렬로 유지됩니다.

현재 스킬 → prepare-work → 작업 전용 문맥 → 네이티브 실행 → 종료·수용 기준 확인 → record-work → 합류

누락·오래된 결과·시간 초과는 완료로 합치지 않습니다. 입력 16 KiB·결과 8 KiB 한도를 넘으면 필요한 근거를 별도 문서로 참조합니다. 실제 토큰 계측이 없으면 미확인으로 남기며 절감률을 추정하지 않습니다. 선택적 토큰 예산은 추가 작업의 시작을 제한하고, 실행 중 호출 비용을 강제 차단하지는 않습니다.

실행 계약·명령·한계

설치 수를 비교한 원본 스킬과 조건부 연결

Superpowers와 Matt Pocock의 역할별 스킬 8개를 공식 최신 커밋에서 다시 다운로드했습니다. 기존 원본도 같은 내용이어서 본문 변경은 없으며, 커밋·라이선스·설치 지표와 연결 근거를 보강했습니다.

incoming 원본 → 검토한 짧은 참조 → 기존 G3 계획·진단 / G5 설계 / G6 행동 테스트 / G7 증거 확인

CLI 설치나 새로운 라우터 없이 25개 활성 스킬을 유지합니다. 테스트·진단은 비교 후보보다 설치 수가 높은 mattpocock/tdd와 diagnosing-bugs를 주 참조로 선정했습니다. 설치 수는 고유 사용자 수나 품질 보증이 아니며, 불필요한 질문·다중 리뷰·upstream 스크립트 실행은 추가하지 않습니다.

설치 수·비교 후보·원본과 연결 위치 · 커밋·해시·선정 기록

ROS 2 작업에만 선택적으로 연결하는 MCP 조회 도구

ROS 2 코어 0.2.0은 실행 환경·QoS·검증 근거를 보강했습니다. ROS 2와 ros-mcp-server가 모두 선택된 프로젝트 작업에서만 MCP 참조를 전달합니다. 일반 ROS 2 개발이나 다른 MCP 작업은 자동 연결되지 않습니다.

ROS 2 + ros-mcp-server 선택 → G5 ROS 2 스킬 → 도구·대상·조회 권한 확인 → stdio 조회 → 관찰 근거 또는 오류

조회 전용 도구 9개를 준비했으며 발행·제어·임의 서비스 호출은 노출하지 않습니다. 로컬 MCP 초기화와 모의 응답 검증은 실제 로봇 연결·안전성 검증과 구분합니다. 최초 5개 레이어 업데이트: 2026-10-24.

검증과 종료

오래되거나 부분적인 결과는 완료 근거가 아닙니다. 통합 검증 후 불필요한 리뷰·수정 반복을 멈춥니다.

538개 후보 패키지, 554개 스킬 진입점을 메타데이터로 점검했습니다. 20개 후보의 절차 일부만 코어에 반영했고 원본 패키지는 활성화하지 않았습니다. 전체 보안·라이선스 감사나 실행 속도 향상을 입증한 것은 아닙니다.
