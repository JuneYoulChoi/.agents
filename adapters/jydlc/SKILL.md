# 사용자 주도 개발 게이트

기존 G0–G7, 스킬, 권한과 검증 계약을 사용한다. 사용자가 지목한 게이트를 진행한 뒤
결과를 보고하고 멈춘다. 다음 게이트로 넘어가려면 별도 호출이 필요하다.

## 호출

Codex에서는 `$jydlc requirements-analysis`, Claude Code에서는
`/jydlc requirements-analysis`처럼 `jydlc` 뒤에 공백을 두고 단계 이름을 입력한다.

| 인자 | 동작 |
| --- | --- |
| 인자 없음 | `workspace-detection`의 읽기 전용 확인을 자동으로 실행한다. 결과를 보여 주고 새 작업이면 요청을 받는다. |
| `start <요청>` 또는 요청만 입력 | `workspace-detection`을 먼저 실행하고 요청 분류와 예상 경로를 미리 본다. |
| `stages` | 단계 이름, 의미, 게이트 ID와 호출 예를 보여 준다. |
| `status [작업 ID]` | 현재 위치, 이전 게이트 결과, 남은 결정과 다음 실행 가능한 게이트를 보여 준다. |
| `inspect <단계 이름>` | 지정한 단계의 목표·준비물·예정 산출물을 보여 준다. |
| `<단계 이름>` 또는 `run <단계 이름>` | 현재 실행 가능한 단계 하나를 수행한다. `workspace-detection`은 시작 환경을 다시 확인할 때도 쓸 수 있다. |
| `resume <결정 또는 복구 근거>` | 기존 대기·차단을 해소하고 현재 게이트의 위치를 보여 준다. |

제어 명령을 먼저 확인한다. 인자 전체가 아래 단계 이름, 공유 하네스
`registry/routing-gates.json`의 `operator_name` 또는 게이트 ID와 정확히 일치하면 해당
게이트 호출로 해석한다. `run`과 `inspect`도 같은 이름을 받는다. 등록되지 않은 이름이
`run` 또는 `inspect` 뒤에 오면 `stages`를 안내한다. 그 밖의 요청 문장은 읽기 전용 미리보기로
처리한다. `stages`, `status`, 다음 호출 안내에는 아래 단계 이름과 레지스트리의
`operator_label`을 표시한다. Runner 호출에는 해석한 게이트 ID를 사용한다.

## 처음 시작할 때

1. `jydlc`를 호출하면 요청을 받기 전에 프로젝트 루트와 Codex 또는 Claude 어댑터를
   읽기 전용으로 확인한다. 외부 하네스 소스는 기존 어댑터 설정이나 이식 가능한 설정의
   locator에서 찾는다. 경로를 찾을 수 없으면 사용자에게
   공유 하네스 경로를 받는다. 실제 원본과 승인 레지스트리의 해시를 설정에 기록된 값과
   대조하고
   `harness_bootstrap.py check --target-root <대상> --harness-root <승인 원본>`으로 설정을 확인한다.
   미설치·충돌 및 확인할 수 없는 항목을 보고한다. 확인에 실패했거나 설치·설정 변경이나
   가드 조치에 승인이 필요하면 G0에서 멈추고 복구에 필요한 정보나 승인을 요청한다.
   확인을 통과했고 인자가 없으면 진행 중인 작업의 상태와 다음 호출을 알려 주거나,
   새 작업에 필요한 요청을 받는다. 진행 중인 작업은 그대로 이어간다.
2. 요청을 받은 뒤 미리보기에 관측한 문서와 작업 상태, 복수 필드 및 근거, 위험도,
   적용 깊이를 표시한다.
   의도한 실제 작업을 구조화한 intake로 기존 Router를 평가한다. 현재 분류는 G1에서
   확인할 초안이다. `docs/architecture/`에서 적용되는 산출물의 누락·노후·확인 필요를 찾아
   게이트 순서와 함께 보고한다. 문서 이름이 달라도 같은 역할의 근거가 있는지 확인한다.
3. 각 게이트에 필요한 입력, 선택된 스킬과 깊이, 담당 역할, 예상 산출물, 현재 차단 사유를
   짧게 표시한다. 파일 변경, 외부 실행, 스킬 실행은 권한이 확인된 단계 호출에서만 수행한다.
   게이트 문서가 필요하면 공유 하네스의 `plan/03-contracts-and-fixtures.md`에서
   **Gate document locations**를 확인하고 예정 경로를 표시한다. 문서를 저장한 뒤에는
   실제 경로를 결과에 적는다.

## 게이트별 확인

| 게이트 | 단계 이름 | 실행 시 확인할 것 |
| --- | --- | --- |
| G0 | `workspace-detection` | 대상·소스 핀·어댑터·권한·훅 또는 수동 가드. 필요한 승인·면제와 차단 사유 |
| G1 | `intake` | 요청 범위, 필드와 근거, 품질·실행 환경, 위험도·깊이, 수용 기준과 미정 결정 |
| G2 | `reverse-engineering` (기존 프로젝트), `architecture-baseline` (신규 프로젝트) | 아키텍처 기준선, 이해관계자와 관심사, 표준·정책 적용성, 문서 공백 |
| G3 | `requirements-analysis` | 승인된 요구사항과 QAS, 변경 영향, 역할·작업 단위와 의존성 |
| G4 | `workflow-planning` | 라우팅이 선택한 기술·설정·검증 준비와 관련 도구·환경의 적용 근거 |
| G5 | `application-design` | 활성화된 패턴·언어·생태계 검토와 설계 결정. 해당 경계의 SOLID·GRASP 근거 |
| G6 | `code-generation` | 승인 범위의 구현·시험, 해당 시 TDD 실패·통과 근거, 품질 결과 |
| G7 | `build-and-test` | 수용 기준별 실제 결과, 산출물 추적, 미검증 조건과 인계 |

## 실행과 이어가기

- 자동 확인 결과는 `intake`에서 재사용한다. 대상·소스·어댑터가 바뀌면 다시 확인한다.
  G0에 필요한 권한·가드 증거와 사용자 확인을 확보한 뒤 G1을 닫는다. 같은 `intake`
  호출에서 두 결과를 함께 확인할 수 있다. `workspace-detection`을 따로 입력할 필요는 없다.
  선택된 스킬 본문과 검증 절차는 해당 게이트를 실행할 때 읽는다. `intake`에서 확인한
  요청의 권한 조건이 바뀌면 그 사유를 표시하고 멈춘다. 분류나 요청이 바뀌면 권고 모드에서는 라우팅을 다시 계산한다.
  영속 작업에서는 기존 되돌림 또는 이전 작업에 연결한 새 시작 절차를 따른다.
- 영속 작업은 intake에 `operator_mode: jydlc`와 사용자가 확인한 G0·G1의
  `initial_checkpoints`를 기록하고 Runner의 `start`를 호출한다. `status`의
  `operator.gate_name` 또는 `operator.gate`가 사용자 요청과 일치하면 `checkpoint`로 연다.
  같은 게이트의 `next` 스킬에 한하여 실행하고 제출한다. 모든 스킬과 근거를
  확인한 뒤 `checkpoint`로 닫고 멈춘다. 기록 형식은 공유 하네스의
  `plan/03-contracts-and-fixtures.md`에서 **jydlc operator evidence** 절을 읽는다.
- 시작 환경에 차단 사유가 없으면 다음 호출로 `intake`를 안내한다. 이후 게이트는 순서대로
  사용자 호출을 받는다. Runner에 실행 스킬이 없는 게이트도 수동 확인 지점으로 남긴다.
  선택된 관심사가 있으면 그 입력·산출물·검증 준비를
  확인하고, 해당 사항이 없으면 라우팅에 근거해 사유를 기록한다. 이때 실행 스킬 결과를
  만들어 제출하지 않는다. 영속 작업은 스킬이 비어 있는 게이트도 `checkpoint`로 닫는다.
- 권고 모드는 전체 Router 투영과 이 대화에서 확인한 게이트 결과를 사용한다.
  작업 상태를 만들거나 다른 세션에서 자동 복원을 약속하지 않는다. 직전 결과와
  증거를 복원할 수 없으면 해당 게이트부터 확인한다. 권고 모드 변경의 마무리 검사는
  기존 G7 절차에서 수행한다. 실제 구현자·검증자 영수증이 필요한 개발에 영속 실행 수단이
  없으면 해당 요구를 충족할 수 없음을 알리고 진행을 기다린다.
- `resume`은 스킬 또는 G0가 중단한 영속 작업에 Runner 재개를 사용한다. 아직 상태를
  저장하지 않은 intake 대기는 새 결정을 반영해 라우팅을 다시 평가한다. 이미 저장된
  라우팅 차단은 기존 작업에 연결해 다시 시작한다. 어느 경우든 재개만으로 게이트를
  실행하지 않는다.
- 분기 비활성은 Router의 근거를 보고한다. 미선택 스킬을 별도로 실행하지 않는다.
  선행 게이트 미완료, 사용자 결정 대기, 권한 문제, 시험 실패가 남으면 다음 게이트를
  실행하지 않는다. 기존 게이트 재개·되돌림 절차를 따르며 완료를 증거로 판정한다.
- 작업 계획에서 허용된 역할과 도구만 사용한다. 실제 위임, 도구 실행, 산출물과 검증
  증거를 구분해 기록한다. 표시할 결과는 단계 이름과 상태, 산출물·검증 근거, 남은 사용자
  결정, 이름으로 입력할 다음 호출이다. 미확인 시험이나 생략된 필수 역할은 완료 증거가 될 수 없다.
